## 3.6 上下文工程

随着智能体系统日益复杂，业界逐渐认识到仅优化提示词已经不够，一个更系统的工程方向随之兴起：**上下文工程**。

> 💡 关于上下文工程的完整介绍，请参阅《上下文工程指南》。

> **要点**：上下文工程强调把“提示词、工具、记忆、用户元数据、缓存与路由”当成一个整体系统来设计。很多稳定性问题的根源是“上下文注入的内容不对/不全/不可控”，而不是“提示词写得不够好”。

> **关键链接**：上下文工程是必要条件但非充分条件。要将精心设计的上下文转化为生产级的可靠行为，还需要 Harness 层的执行治理，包括工具执行控制、状态持久化、安全边界和生命周期管理（详见 [9.2 节](../09_agentops/9.2_harness.md) Harness 架构）。

### 3.6.1 上下文工程在智能体中的关键角色

**上下文工程** 是指系统地管理、优化和编排输入 AI 模型的所有信息的技术。在智能体系统中，它的核心职能是把长期记忆（数据库、知识库）中的海量信息经过筛选、压缩和编排，高效注入短期记忆（上下文窗口）。

与一般的 LLM 应用相比，智能体的上下文工程需要特别关注：

- 工具的动态注入与卸载
- 内存（episodic、semantic、procedural）的分层管理
- 用户元数据与权限隔离
- 缓存与路由的动态调整

### 3.6.2 核心约束：有效上下文远小于标称值

模型宣称的上下文窗口规模（如 200K tokens）并不反映实际推理能力，原因有两点：

1. **上下文腐烂（Context Rot）**：即便模型能处理长序列，推理准确率也会随上下文长度增加而逐步衰减。这种下降是渐进的，并非突然断崖。

2. **中段丢失（Lost in the Middle）**：模型倾向于关注开头（系统提示）和结尾（最新结果），对中间内容重视不足。关键信息一旦淹没在大量日志中，就容易被忽略。

经验上，编码智能体通常只能有效利用上下文窗口的一小部分；窗口被噪音填满时，推理准确性与指令遵循会明显下降。

### 3.6.3 系统提示词的“高度”校准

系统提示词需避免两个极端：


- **过度硬编码**：`IF 包含“代码” THEN 调用 tool_A` 在边界情况下失效，需不断补丁。
- **过度抽象**：`你是聪明助手，按最佳实践完成任务` 指导不足，易导致猜测。

合适的做法是提供启发式指导而非严格规则，例如：“你是编码助手。修改代码时：(1) 搜索相关文件理解上下文 (2) 提出方案并说明原因 (3) 实施后运行测试 (4) 失败则分析并迭代（最多 3 次）”。这样的指导既具体又灵活。

### 3.6.4 四大核心策略

**“有限的上下文窗口”** 与 **“无限的知识需求”** 之间存在矛盾。上下文工程要解决的核心问题是：*如何在不超出 Token 预算的前提下，让 AI 获得最精准、最相关的决策依据？*

常用方法可以抽象为四种信息处理原语：持久化上下文、筛选上下文、压缩上下文、隔离上下文。放进同一条流水线看，持久化负责“把信息留在系统外”，筛选负责“把相关内容找回来”，压缩负责“把必要内容变短”，隔离负责“把不该看到的内容挡在外面”。

#### 1. 持久化上下文

持久化上下文是指把信息存储到外部系统，突破即时上下文窗口的限制。大模型的上下文窗口昂贵且易失，持久化上下文要构建的是一个 **外部记忆体**，而不只是简单的日志记录。智能体借此“记住”跨越数天甚至数月的交互细节，无需每次重新输入。关键操作包括：
- **索引化**：将非结构化文本通过嵌入转化为向量，从一开始就为后续检索做好准备。
- **结构化存储**：将关键实体（如用户偏好、项目配置）提取存入 SQL/NoSQL 数据库。
- **状态快照**：定期保存智能体的思维状态，支持断点续传。

```python
class ContextWriter:
    """将重要信息写入持久化存储"""

    def __init__(self, memory_store):
        self.memory = memory_store

    def persist_user_preference(self, user_id: str, preference: dict):
        """保存用户偏好，供后续会话使用"""
        self.memory.write(
            key=f"user:{user_id}:preferences",
            value=preference,
            ttl=86400 * 30  # 保留 30 天
        )

    def persist_task_context(self, task_id: str, context: dict):
        """保存任务上下文，支持跨会话恢复"""
        self.memory.write(
            key=f"task:{task_id}:context",
            value={
                "state": context,
                "timestamp": datetime.now().isoformat(),
                "checksum": self._compute_checksum(context)
            }
        )
```

它的应用场景包括：

- 用户偏好和个性化设置
- 长期任务的进度保存
- 跨会话的知识积累

**工具设计中的 Token 效率原则**：设计工具时应优先考虑 Token 消耗。例如 `search_contacts(query)` 只返回匹配结果，`list_contacts()` 返回完整列表，前者的 Token 效率高出一个数量级。原则是 **让工具 API 支持查询与过滤，而非一次性加载全集**。

#### 2. 筛选上下文

筛选上下文是指从海量信息中检索最相关的内容，只向模型展示当下决策所需的信息，RAG 即属此类。关键操作依次为向量检索（语义相似度）→ 重排序（精确性）→ Token 预算控制（选择 Top-K）。

```python
def select_context(query: str, candidates: List[str], budget: int = 4000) -> List[str]:
    """多阶段检索：粗筛 → 精排 → 预算截断"""
    coarse = vector_search(query, candidates, top_k=20)   # 语义粗筛
    ranked = reranker.rank(query, coarse, top_k=10)        # 交叉编码器精排
    selected, used = [], 0
    for doc in ranked:
        tokens = count_tokens(doc)
        if used + tokens <= budget:
            selected.append(doc)
            used += tokens
    return selected
```

检索优化技术详见 [3.4 RAG 系统设计与优化](3.4_rag_advanced.md)。

#### 3. 压缩上下文

压缩上下文是指通过额外计算（LLM 摘要），在保留关键信息的前提下大幅减少 Token 占用，即“用时间换空间”。关键操作包括对话摘要（保留最近 N 轮，更早的压缩为摘要）、信息提取（只保留结构化字段）和渐进式遗忘（周期性压缩早期记录）。

一种经实证验证高效的变体是 **结构化笔记**：智能体在执行过程中定期把关键发现写入外部文件（如 `NOTES.md`），重启会话时直接读取笔记恢复工作记忆，而不是压缩整个对话历史。笔记比自由文本摘要更紧凑、更易检索，并支持跨会话延续。

详细实现见 [3.2 短期记忆管理](3.2_short_term_memory.md)。

#### 4. 隔离上下文

隔离上下文是指把任务拆分给不同的子智能体（Sub-agents），实现信息隔离和关注点分离，体现“最小特权原则”。与其让全能智能体面对混杂的上下文，不如让“编码智能体”只看代码、“客服智能体”只看 FAQ，这样既提升准确性，也强化安全边界。

```python
def route_to_subagent(query: str, context: dict) -> str:
    """按意图将请求路由到专用子智能体，每个子智能体只看到自己领域的上下文"""
    intent = classify_intent(query)  # coding / support / analysis
    subagent = AGENT_REGISTRY[intent]
    filtered_ctx = filter_context_by_domain(context, domain=intent)  # 隔离
    return subagent.run(query, context=filtered_ctx)
```

关键操作包括上下文路由（按意图分发）、防火墙设计（敏感数据隔离）和独立状态机（各子智能体的历史互不污染），详见 [第 5 章 多智能体协作](../05_collaboration/5.1_architectures.md)。

### 3.6.5 实战：构建统一的上下文结构与管理器

工程落地时，强类型、标准化的上下文结构能大大简化调试与监控。建议用统一的 `ContextPack` 结构取代零散的字符串拼接。该结构必须内置 `trace_id` 与 `span_id`，使其日志与系统其余部分（如互操作协议、可观测性平台）完全对齐。

```python
import uuid
from typing import List, Dict

class ContextPack:
    """标准化的上下文数据包——所有字段对齐可观测性体系"""
    def __init__(self, trace_id: str = None):
        self.trace_id = trace_id or str(uuid.uuid4())
        self.span_id = str(uuid.uuid4())
        self.system: str = ""              # 身份与规则提示词
        self.tools: List[Dict] = []        # 当前可用工具 Schema
        self.memory: List[Dict] = []       # 长/短期记忆、压缩历史及偏好
        self.evidence: List[Dict] = []     # 检索到的事实片段（需含 source_id）

class ContextManager:
    """四大策略的统一编排入口"""

    def prepare_context(self, query: str, user_id: str,
                        history: List[dict], tools: List[dict]) -> ContextPack:
        pack = ContextPack()
        # 1. 持久化 → 加载用户偏好
        pack.memory += self.load_user_prefs(user_id)
        # 2. 筛选 → 检索相关知识
        pack.evidence = self.select_relevant(query, max_tokens=4000)
        # 3. 压缩 → 摘要对话历史
        pack.memory += self.compress_history(history, max_tokens=2000)
        # 4. 隔离 → 过滤当前任务相关的工具
        pack.tools = self.filter_tools(query, tools)
        return pack
```

`ContextPack` 是一个带来源标签的标准容器：顶部是全链路追踪信息，中间是系统提示词与工具定义，底部是记忆和证据片段。

### 3.6.6 进阶模式：应对复杂场景

智能体系统规模扩大后，会面临上下文腐烂、工具过载等问题，下面是四种应对方案。

#### 1. 上下文腐烂与卸载

工具调用不断累积，历史随之膨胀，模型推理性能会断崖式下跌。解决方法是把这些内容卸载到外部存储，而不是硬塞进短期记忆（超过 Token 阈值的结果写入 `.log`，对话历史写入 `.json`），需要时再检索。这比持续压缩短期窗口更高效。

#### 2. 两阶段缩减策略

卸载不足以解决问题时，采用渐进式缩减：


- **第一阶段（紧凑化）**：无损、可逆。剥离能从外部重建的信息（如文件写入只保留路径），保留最近调用作为 Few-shot 示例。
- **第二阶段（摘要化）**：有损但带保险。生成摘要前先备份，保留最后 6 次完整调用维持连贯性。

紧凑化可逆，摘要化不可逆，因此应优先充分紧凑化。

#### 3. 动态上下文发现

这一模式遵循“少即是多”：不在系统提示中列举所有工具，而是把工具定义同步到文件（`.tools/` 目录），让智能体按需用 `cat` 或 `grep` 自行发现。这样可以显著降低初始上下文的 Token 消耗，对工具众多的场景尤其有效。

#### 4. 分层行动空间

工具过多会导致上下文混淆与幻觉。解决方法是采用三层架构：

- **L1（原子）**：`read_file, write_file, shell` 等基础操作，固定且缓存友好
- **L2（沙箱）**：格式转换、语音识别等工具，智能体自行用 `ls/--help` 探索
- **L3（代码）**：复杂计算写成 Python 脚本，只返回摘要

模型只需调用统一的 L1 接口，通过 L1 执行 L2/L3 的工具，从而大幅降低认知负荷并提高稳定性。

### 3.6.7 智能体工程师的核心技能

构建可靠的智能体需要 **提示词工程 × 软件工程 × 产品设计** 的交叉能力，业界开始把这一角色称为“智能体工程师”或“上下文工程师”。其核心技能包括：

* **上下文预算与裁剪**：权衡成本、延迟与信息量，制定可执行的预算策略。
* **信息检索与证据链**：设计检索、重排序与引用格式，让答案可追溯、可审计。
* **工具与接口设计**：将复杂能力封装为稳定的原子工具，通过 Schema 降低参数幻觉。
* **评估与回归**：将需求转化为验收标准，维护回归样例集并量化改动收益。
* **安全与隐私**：处理提示词注入、数据脱敏、权限分级与保留期治理。
* **可观测与故障恢复**：用轨迹日志定位失败模式，设计重试、回退与熔断机制。

### 3.6.9 被动上下文 vs. 动态技能：实证对比

2026 年初，[Vercel 的公开评估](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)对比了两种传递框架知识的方式：**被动上下文（AGENTS.md）** 与 **动态技能（Skills）**。

在 Next.js 16 API（超出模型训练数据的框架特性）的评估套件上，四种配置的表现如下：

| 配置 | 成功率 |
| :--- | :--- |
| **无文档（基线）** | 53% |
| **Skills（默认）** | 53% |
| **Skills + 显式指导** | 79% |
| **AGENTS.md（压缩索引）** | 100% |

被动上下文的优势在于信息始终在系统提示词中可用，智能体无需主动激活技能，也就省去了“先参考文档还是先探索代码”的决策摩擦。一份压缩的 8KB 文档索引（从原 40KB 文档压缩而来）嵌入系统提示后，达到了完美的适应性。

可见在上下文有限的情况下，**精心设计、无需激活的被动信息往往优于可选的动态工具**。

> **补注**：上述数据来自特定项目的内部评估，实际效果因项目复杂度、框架特性和 LLM 能力而异，建议在自身项目中用类似评估验证。

### 3.6.10 记忆安全与隐私

记忆系统一旦“能写能读”，就能长期影响智能体的行为，安全与合规要求也随之提高。工程上建议把记忆与上下文视为一类“可被攻击、可被治理”的数据资产。

#### 3.6.10.1 记忆投毒与间接注入

记忆投毒是指攻击者通过对话、文档或工具输出，把恶意指令写入长期记忆或知识库，从而在后续检索中反复触发。常见防护思路包括：

- **写入前审查**：将“可写入记忆”的内容分为白名单字段（偏好、事实、已验证结论），拒绝写入指令性文本。
- **分区与隔离**：将“用户偏好”“任务轨迹”“外部知识”分库存储，检索时按任务域选择分区，避免跨域污染。
- **带证据的写入**：要求每条可持久化记忆携带来源与证据指针，支持事后回放与撤销。

#### 3.6.10.2 保留期与删除权

记忆越持久，风险越大。保留期应当做成明确的策略，不能“默认永久保存”：

- **按类型设置保留期**：偏好可长存，任务轨迹与日志应短存，敏感字段应不落盘或强加密。
- **可删除与可追溯**：支持按用户、会话、记忆条目删除，并确保下游索引与缓存同步失效。
- **最小化原则**：能从原始数据推导出的信息不要重复存储；能用摘要表达的不要存全文。

保留期策略可以做成可配置的规则集，例如：

```yaml
memory_retention:
  preference:
    ttl_days: 365
  episodic_trace:
    ttl_days: 30
  tool_outputs:
    ttl_days: 7
  pii_fields:
    persist: false
```

#### 3.6.10.3 隐私与脱敏清单

落地时可用以下最小清单自检：

- 记忆写入前是否做了 PII 识别与脱敏
- 是否区分“用户可见摘要”和“受控日志细节”
- 是否记录了每条记忆的 `source`、`timestamp`、`trace_id`
- 是否支持删除与撤销，并能覆盖向量索引与缓存
- 是否为跨租户检索设置了硬隔离与权限校验

#### 3.6.10.4 授权类记忆：范围比事实更容易丢失

前三小节关注的是“写进去的内容对不对”。还有一类失效与内容真假无关：**事实被完整保留，限定条件却在摘要中蒸发了**。

设想用户在一次对话里说：

```text
这个月的促销活动，你可以自行批准 15% 以内的折扣。
```

这句话带有三个限定：时间（这个月）、对象（这次促销活动）、额度（15% 以内）。记忆压缩却很容易把它归纳成一条更“干净”的偏好：

```text
用户允许 15% 以内的折扣。
```

从语义上看这句话并不算错：额度是真的，“用户允许”也是真的。丢掉的是**什么时候、对哪件事、在什么前提下**允许。几个月后另一个活动触发检索，智能体读到这条记忆，会认为自己一直握有这项授权。一次**事务级的临时批准，就这样变成了长期的常设权限**，而这个变化没有经过任何审批。

这类问题难以发现，因为它不表现为错误答案：智能体的推理链条完整，引用的记忆真实存在，行为也与记忆一致，只有把记忆回溯到原始对话，才能看出授权范围被放大了。相比之下，3.6.10.1 节 的记忆投毒至少还留下了一段可疑的注入文本。

工程上的处理办法是**按授权语义给记忆分类，而不是一律当作偏好**：

| 记忆类型 | 典型内容 | 可否长期留存 | 关键要求 |
| --- | --- | --- | --- |
| 偏好类 | 「摘要写短一些」 | 可以 | 记录来源即可 |
| 事实类 | 「客户账期为 Net 60」 | 需要复验 | 必须可被更新的权威源覆盖 |
| 策略类 | 「超过 5 万需二级审批」 | 不宜自存 | 引用策略系统，不复制成记忆 |
| 授权类 | 「这次你可以直接批」 | **不可以** | 绑定作用域，用完即失效 |

授权类记忆最容易出问题，因为它在自然语言里与偏好类几乎没有区别。稳妥的做法是让这类记忆在写入时就带上作用域，并且**默认过期**：

```yaml
memory:
  statement: 可自行批准 15% 以内的折扣
  type: authorization        # 与 preference 区分，检索时单独处理
  scope:
    campaign_id: CMP-2026-08
    max_discount: 0.15
  granted_by: marketing_manager
  valid_until: 2026-08-31    # 授权类记忆必须有终止条件
  auto_renew: false
```

检索阶段还需要在语义相似度之外加一道判断：这条记忆的作用域是否覆盖当前任务。命中但作用域不匹配时，正确的行为是**忽略它并按无授权处理**，而不是把它当作弱证据参考。

从人类行为中归纳出的规律也是如此。智能体观察到过去多次「它建议暂缓、人类选择放行」，可以得出一条有价值的观察：

```text
同类交易通常会被放行。
```

但这条观察**不能**自动演化成：

```text
同类交易以后可以由我直接放行。
```

前者描述组织行为，后者主张自身权限。两者之间隔着一次审批，这个边界不应由记忆归纳来跨越。可行的做法是让重复出现的人工放行触发一次**策略复审**，由人决定是否正式扩大智能体的权限；复审通过之前，智能体的权限维持原状。


以上是抽象原则。下面先介绍一种跨会话的记忆整合机制及其真实产品，再给出一个贴近真实产品、但明确标注边界的示意案例，把持久化、压缩、隔离与治理串成完整闭环。

### 3.6.11 “做梦”机制：跨会话记忆整合

“做梦”（Dreaming）机制是一种新兴的记忆管理模式，灵感来自睡眠期间大脑的记忆整合过程，尤其适合长期运行的智能体系统。

#### 工作原理

积累足够数量的会话后，后台触发一个 **专用记忆整合 Agent**（类似“梦者”），执行以下四个阶段：

1. **定位**（Locate）：扫描过去 N 个会话的记忆存储，识别重复出现或稳定的知识点、模式与经验。
2. **收集**（Collect）：把这些稳定内容从分散的会话记忆中收集起来，去重并标记源会话。
3. **合并**（Merge）：将相似内容合并，生成更紧凑、更通用的总结（如“处理 API 错误的最佳实践”）。
4. **组织**（Organize）：将合并后的知识重新组织回外部记忆库（如 MEMORY.md 的 topic 文件），供未来会话检索。

#### 互斥与安全保障

多个会话同时触发梦者会产生竞争，通常采用 **PID + 时间戳的文件锁** 互斥：

```python
lock_file = f"~/.claude/projects/{project_id}/memory/.dreamlock"
# 格式：{pid}:{timestamp}
# 只有最早的进程获得独占权
```

梦者 Agent 本身使用受限工具集：只读访问 bash（查询文件）和对 `memory/` 目录的写权限，防止误修改项目代码。

#### 实施建议

- **触发阈值**：每 5-10 个会话或每周一次定期触发。
- **隔离上下文**：梦者运行时与主会话隔离，使用独立的系统提示与工具定义。
- **版本管理**：整合前备份原始会话记录，支持事后审计与回滚。

#### 真实案例：OpenAI Dreaming

OpenAI 在 2026 年公开了一套官方名称就是 **Dreaming** 的后台记忆整合系统（见 [Dreaming: Better memory for a more helpful ChatGPT](https://openai.com/index/chatgpt-memory-dreaming/)，2026-06-04），可作为本节机制的真实产品对照：

- **从显式保存到后台综合**：ChatGPT 记忆经历了三个阶段：Saved memories（2024-04，依赖用户显式说“记住……”）→ 首版 dreaming（2025-04，即 Dreaming V0，开始引用聊天历史自动整理）→ Dreaming V3（2026）。Dreaming 用一个后台进程从大量会话中**综合**记忆状态，不再依赖逐条显式指令，这对应本书 §3.1 把记忆重新定义为“持续状态维护”，以及静态/动态画像的分层。
- **三条评测目标**：官方用三条标准衡量记忆质量：带着有用上下文前进、遵循偏好与约束、随时间保持时效。最后一条与本书反复强调的“时间推理 / 自动遗忘”一致：行程结束后，记忆应从“将在 7 月去新加坡”自动修订为“已于 2026 年 7 月去过新加坡”。
- **规模化是工程约束**：OpenAI 报告，近期改进把向免费用户提供该能力所需的算力降低了约 5×，向免费用户推广才成为可能。可见“做梦”的难点常常不在算法，而在**以可接受的成本，在海量用户与多年时间跨度上持续维护记忆**。

### 3.6.12 案例：Claude Code 的 autoDream 与基于公开机制的实现

> 说明：Claude Code 中确有名为 autoDream 的后台记忆整合功能，对应尚未正式发布的 `autoDreamEnabled` 设置。它由社区从 Claude Code 的 `cli.js` 中发现，官方文档尚未收录，调度策略与内部实现也未公开。因此本节不复述其内部实现，而是以官方文档公开的 `CLAUDE.md`、auto memory、`/memory`、`/compact`、subagents 与 hooks 等机制为基础，给出一个功能相近的**工程示意**。

#### 3.6.12.1 官方文档已经公开的记忆机制

根据 Anthropic 公开的 Claude Code 文档，以下机制可以作为“记忆整合器”可靠的设计基础：

- **层级化指令记忆**：`CLAUDE.md`/`CLAUDE.local.md` 会按目录层级加载；当前工作目录以上的文件在启动时加载，子目录下的文件在读取相关文件时按需加载。
- **项目级 auto memory**：每个项目对应 `~/.claude/projects/<project>/memory/`；其中 `MEMORY.md` 是入口文件，首 200 行或 25KB 会在每次会话开始时加载，其余 topic 文件按需读取。
- **显式管理入口**：`/memory` 可以查看当前加载的记忆文件、切换 auto memory，并直接打开和编辑记忆目录。
- **上下文压缩机制**：`/compact` 与自动 compact 会在上下文逼近上限时摘要历史；Claude Code 也会为 `claude --resume` 做后台会话摘要。
- **隔离式子智能体**：subagent 运行在独立上下文中；若启用 `memory` 字段，还可拥有单独的持久化记忆目录。
- **可编排触发点**：hooks 提供 `PostCompact`、`TaskCompleted`、`SubagentStop` 等事件，可作为记忆整理流程的触发器。

这些都是文档可证实的能力边界；更深一层的调度策略与内部实现，官方并未公开。

#### 3.6.12.2 基于公开机制的 autoDream 式架构

在 Claude Code 的公开机制之上自行实现后台记忆整合，可以组织成下面的维护流程。它是本书的示意实现，不是 autoDream 的内部实现：

1. **触发**：在 `PostCompact`、`TaskCompleted`、`SessionEnd` 等 hooks 上触发，或由外部定时任务周期性唤起。
2. **读取**：检查项目的 `CLAUDE.md`、auto memory 目录，以及需要长期积累知识的 subagent memory。
3. **整合**：把稳定、可复用的经验写回 topic 文件，把 `MEMORY.md` 保持为简洁索引，避免超出首屏加载预算。
4. **回流**：下一次会话启动时，`CLAUDE.md` 与 `MEMORY.md` 头部自动进入上下文；更细的主题文件继续按需读取。

用伪代码表示，大致是下面这样的组合：

```python
def auto_dream(event):
    project_memory = load_auto_memory_dir()
    instruction_files = load_claude_md_hierarchy()
    agent_memories = load_subagent_memories()

    stable_notes = consolidate(
        instruction_files=instruction_files,
        project_memory=project_memory,
        agent_memories=agent_memories,
        trigger=event,
    )

    rewrite_memory_index(
        memory_dir=project_memory,
        notes=stable_notes,
        max_head_lines=200,
        max_head_bytes=25 * 1024,
    )
```

无论是否启用 autoDream，关键都在于是否把**压缩、分层、按需加载、可审计编辑**这些公开机制连接成闭环。

#### 3.6.12.3 哪些内容不能当作 Claude Code 官方事实

为避免把示意架构误读为产品说明，下面这些说法都不应写成“Claude Code 已经如此实现”：

- autoDream 已正式发布并有官方文档说明。它目前只对应一个尚未正式发布的 `autoDreamEnabled` 设置。
- 社区分析得出的触发条件（如“24 小时 + 5 次会话 + 互斥锁”）是稳定、有官方承诺的行为。
- 官方使用了本文所写的 `~/memories/` 目录结构、`findRelevantMemories()` 函数或特定向量嵌入流程。
- 官方要求只能通过某个专用 memory API 写入，或采用了文中的特定淘汰/冲突消解启发式。

稳妥的说法是：**autoDream 真实存在，但尚未写入官方文档；官方公开了可拼装同类能力的机制，如何组合成后台记忆整合器，属于工程实现选择。**
